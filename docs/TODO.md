From the comparison of 2026-11-25 (`QUESTIONS.md`, "Comparison with ShaderGlass": its public pages only, nothing measured). Each entry is tagged **gap** (ShaderGlass does it, Phoxium does not), **check** (probably covered or a doubt to verify), **decision** (the owner chooses a direction) or **by design** (not planned, to confirm). The project's differentiator is the physical model, not the shader library, so most of these are the owner's call.

- [ ] **gap, decision: an overlay without choosing a window (Desktop Glass).** A transparent window that shades whatever is behind it. Phoxium captures a window or a whole monitor and has click-through; the pieces of an overlay exist (the output window is already hidden from screen captures when a whole monitor is the source, the click-through option passes the mouse), what is missing is a region source: capture the screen area behind the output window, with the output excluded from its own capture. Decide whether it is a goal; if so, a design note first (the focus rules, the moving and resizing of the region, the cost of capturing the monitor).
- [ ] **gap: motion clarity at high refresh (black frame insertion, a rolling beam scan).** ShaderGlass had black frame insertion in its alpha builds and moved it, with a CRT beam simulator, to a separate app (ShaderBeam). Phoxium models the afterglow (persistence) but not the scan: on a 240 or 300 Hz panel a rolling scan of the beam at the refresh rate would be a physical feature, not an effect. First look at what a 300 Hz panel shows with the current persistence (the 240 Hz bullet of the second-PC session, and the 300 Hz results in `QUESTIONS.md`), then decide.
- [ ] **gap: hardware and system reach.** ShaderGlass needs a DirectX 11 GPU and Windows 10 2004 or later (and runs on Linux through Wine); Phoxium needs Vulkan 1.3 and states Windows 11. ## Ideas to scope (new features, the owner decides)

- [ ] **A GBC (Game Boy Color) target: a new input step, the same CRT chain after it.** The chain stays as it is; what is new is a step at its head that transforms the source colours into what the target device would show, so that a Game Boy Color game (an emulator window, or a capture of the console) reaches the tube with the colours of the handheld, as accurate as the sources allow, before the beam and the mask render it. A list of targets, the Game Boy Color first. **Why:** an emulator shows the raw 15-bit colour (5 bits per channel, expanded to 8) straight on an sRGB display, saturated; the reflective screen of the handheld mixed the channels and had a washed-out gamut, which emulators approximate with a correction (a 3 x 3 channel mix and a gamma step). **Sketch:** a native-to-native slot placed first in the chain (before `signal`), an exact identity when the target is `none` (the default, bit-exact like the other optional stages: `Stage::is_identity`), driven by a data-only target profile (a TOML file like the tube presets, each value with its source): the transfer of the source codes, a 3 x 3 matrix, an output transfer, optionally a quantisation (the 5 bits of the GBC) and, for a monochrome target (the original Game Boy), a palette of four shades taken from the luminance; chosen in the Source panel, remembered in the per-game profile (the existing mechanism) and given on the command line (`--source-colour <target>`). Nearby pieces that do **not** do it: the source transfer of `decode` (identity, sRGB, ...), and the gun law, the white balance and the colour sets, which describe the tube and not the source. **Checks:** an f64 oracle of the transform in `crt-model` and a GPU analytic test, as for every stage; the default must leave every picture byte-identical (the byte-comparison of the optics fix is the model). **Sources and licence:** public measurements or studies of the Game Boy Color panel, and the correction formulas that circulate (most live in GPL emulators: take numbers and measurements, never code, the project policy is inspiration only); a value with no source is marked as an estimate, as in `params/*.toml`. **Questions:** (1) in `decode`, which already applies the source transfer, or in a slot of its own (recommended: its own slot, so the default stays bit-exact and the stage tests stay uniform); (2) which targets after the GBC (the Game Boy Advance with and without its front light, the original Game Boy, the Super Game Boy palettes, other consoles with a known colour quirk), each one a data file with its sources and none before the first works; (3) whether a captured frame that is not 5-bit quantised should still be transformed (probably yes: the transform acts on the colours, not on the quantisation). **Decided 2026-11-25 (owner):** (1) its own slot; (2) every target: all the Nintendo hardware and the hardware of other makers (Sega, Atari, Commodore, Amstrad and the like), studied first, one data file each; (3) a frame that is not 5-bit quantised is transformed as well. **Study, first pass done 2026-11-25** (`QUESTIONS.md`, "Study: source colour targets": three kinds of transform, the quality of the data per target, the gaps, the sources). **Next:** the rest of the research (the primary pages for the C64, the CPC, Sega and Atari, and the targets with no data yet), then the design note, before any code.
