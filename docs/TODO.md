## Ideas to scope (new features, the owner decides)

- [ ] **A GBC (Game Boy Color) target: a new input step, the same CRT chain after it.** The chain stays as it is; what is new is a step at its head that transforms the source colours into what the target device would show, so that a Game Boy Color game (an emulator window, or a capture of the console) reaches the tube with the colours of the handheld, as accurate as the sources allow, before the beam and the mask render it. A list of targets, the Game Boy Color first. **Why:** an emulator shows the raw 15-bit colour (5 bits per channel, expanded to 8) straight on an sRGB display, saturated; the reflective screen of the handheld mixed the channels and had a washed-out gamut, which emulators approximate with a correction (a 3 x 3 channel mix and a gamma step). **Sketch:** a native-to-native slot placed first in the chain (before `signal`), an exact identity when the target is `none` (the default, bit-exact like the other optional stages: `Stage::is_identity`), driven by a data-only target profile (a TOML file like the tube presets, each value with its source): the transfer of the source codes, a 3 x 3 matrix, an output transfer, optionally a quantisation (the 5 bits of the GBC) and, for a monochrome target (the original Game Boy), a palette of four shades taken from the luminance; chosen in the Source panel, remembered in the per-game profile (the existing mechanism) and given on the command line (`--source-colour <target>`). Nearby pieces that do **not** do it: the source transfer of `decode` (identity, sRGB, ...), and the gun law, the white balance and the colour sets, which describe the tube and not the source. **Checks:** an f64 oracle of the transform in `crt-model` and a GPU analytic test, as for every stage; the default must leave every picture byte-identical (the byte-comparison of the optics fix is the model). **Sources and licence:** public measurements or studies of the Game Boy Color panel, and the correction formulas that circulate (most live in GPL emulators: take numbers and measurements, never code, the project policy is inspiration only); a value with no source is marked as an estimate, as in `params/*.toml`. **Questions:** (1) in `decode`, which already applies the source transfer, or in a slot of its own (recommended: its own slot, so the default stays bit-exact and the stage tests stay uniform); (2) which targets after the GBC (the Game Boy Advance with and without its front light, the original Game Boy, the Super Game Boy palettes, other consoles with a known colour quirk), each one a data file with its sources and none before the first works; (3) whether a captured frame that is not 5-bit quantised should still be transformed (probably yes: the transform acts on the colours, not on the quantisation). **Decided 2026-11-25 (owner):** (1) its own slot; (2) every target: all the Nintendo hardware and the hardware of other makers (Sega, Atari, Commodore, Amstrad and the like), studied first, one data file each; (3) a frame that is not 5-bit quantised is transformed as well. **Study, first pass done 2026-11-25** (`QUESTIONS.md`, "Study: source colour targets": three kinds of transform, the quality of the data per target, the gaps, the sources). **Built 2026-11-25 (GBC, GBA and SNES):** the slot `target` at the head of the chain, the parameter `source_colour_target` (`none`, `game_boy_color`), the data-file format (`presets/targets/`, `src/targets.rs`, two kinds, `matrix` and `curve`, with provenance per value), the profile field `colour_target`, the oracle and the GPU test; the three targets are the formulas and the table of the near.sh article (the Game Boy Color: unknown author; the Game Boy Advance: Talarubi, tuned by eye; the SNES: Overload, a look and not the console's output; no instrument measurement: estimates). **An audit of all targets was done 2026-11-25** (`QUESTIONS.md`, "Audit of the colour targets": every platform, its data, verdict, transform kind and licence); the order it proposes: (1) the Super Game Boy palettes (hardware data, a 4-colour mono palette kind), (2) the Mega Drive DAC curve (measured, an 8-entry curve with a choice of the emulator's input step), (3) the C64 and NES (measured signal data, driven through the `composite` model, a design note first), (4) CGA RGBI (a measured 16-entry remap), (5) colorimetric Game Boy Color and AGS-101 profiles (the latter needs the data author's permission). Not done: the `--set source_colour_target=...` is the only command-line way (no dedicated `--source-colour` flag), the menu shows the value in the Source panel as a plain choice (no label or notes of the data file yet), and the **other targets and kinds**, each a transform that does not exist yet: the 3D table of the GBCC emulator for the Game Boy Color (a photographed table, better than the formula), the monochrome palettes (the original Game Boy, the Super Game Boy), the palette remaps (the CPC, ZX Spectrum, Genesis, Master System, Amiga, Atari ST: they need the emulator's palette named, to match the pixels to), the composite-generated palettes (NES, C64, Atari 2600 and 8-bit, which could reuse the `composite` model); each waits for its data (the primary pages for the C64, the CPC, Sega and Atari, and the targets with no data yet, `QUESTIONS.md`). Live check outstanding: look at a real Game Boy Color emulator window with the target on and off.
