# Changelog

All notable changes to this project are documented here.
The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/) and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html) (while below 1.0.0, a minor bump may break things).

Every change goes under `## [Unreleased]` as it is made. Publishing renames that section to the new version and date (see `ENV.md`).

## [Unreleased]

### Added

- **Phosphor type** (`phosphor_type`, menu Phosphor panel, first row): P22 (the colour tube, the default, unchanged bit for bit) or a monochrome tube from registered or catalogue phosphor data: P4 (white, black-and-white TV), P31 (green, oscilloscopes and many green monitors), P1 (green, early green screens), P39 (long-persistence green, as in the IBM 5151; its decay is a one-point approximation) and the Philips yellow data-display blend. A monochrome type shows the brightness (BT.601 luma) of the source in the phosphor's own colour, with no mask, and its own afterglow; P1 and P39 smear strongly at 60 Hz, as the real phosphors did. Colours outside the display's sRGB range are clipped by the output as before. Sources and approximations in CRT.md "Phosphor types" and QUESTIONS PHY-19; CRT.md's Wolf and Deubel (1997) figure is corrected.
- **Persistence blend** (`phosphor_persistence_blend`, menu Phosphor panel, second row; owner request 2026-11-21: "the persistence is too much"): one slider from 0 to 1 for the whole afterglow trail, the measured phosphor decay and the extra afterglow together. 0 shows no trail at all, 1 the full trail exactly as before (bit for bit), values in between mix the two linearly. A still picture keeps its brightness at any value, and moving the slider takes effect at once (no restart, no flash).

### Changed

- **The default trail is now half as strong:** the bare defaults and all 10 shipped presets set the persistence blend to 0.5. Measured through the whole chain (white bar moving on black, 60 Hz, green, 8-bit codes): blend 1 (the old look) 212 and 57, 44, 37, 33 one to four frames behind; blend 0.5 (the new default) 222 and 42, 32, 27, 24; blend 0 230 and no trail. Set it to 1 in the Phosphor panel for the previous, full trail. Settings files and your own presets saved before this version have no value for it, so they get the new 0.5 too.

### Fixed

- The Phoxium window has a taskbar button again, with its icon and title, in the framed window and in fullscreen (owner report 2026-11-21). Since the framed window was made non-activating (2026-11-19, so that starting or clicking it never takes the focus from the game), Windows gave it no taskbar button, and the fullscreen output never had one (it was a tool window). Both modes now ask for a button explicitly (`WS_EX_APPWINDOW`, no tool window). The window still never takes the focus when it starts, presents or is clicked; clicking its taskbar button, or picking it with Alt+Tab, is meant to hand the foreground straight back to the window you were in (the existing hand-back). Covered by unit tests of the window styles; not yet checked live on the desktop.

## [0.4.0] - 2026-11-21

### Changed

- The project is renamed **Phoxium** (it was called ultimateCRT up to v0.3.0). The program is `phoxium.exe`, the window titles, the menu, the About section and the version resources say Phoxium, and the release zip is `phoxium-vX.Y.Z-windows-x64.zip` on the GitHub repository `arnaud-sintes/Phoxium` (the repository is renamed from `arnaud-sintes/ultimateCRT`; GitHub redirects the old links, and the v0.2.0 and v0.3.0 downloads keep their `ultimatecrt-...` names).
- The settings folder is now `%APPDATA%\Phoxium`. At the first start, when that folder does not exist yet, the app copies `%APPDATA%\ultimateCRT` into it (settings, your presets, export and import folders, game profiles, burn-in state); the old folder is left untouched and nothing in the new one is overwritten. A failed copy prints a warning, starts with the defaults and is tried again at the next start. Tests: `migrate` unit tests on temporary folders.
- The README is now a short user guide; the detailed reference (developer options, every menu section, recipes, the optional modules) moved to `docs/REFERENCE.md`, which the release zip also carries.
- The release zip no longer contains the `pixel-demo` test source (owner decision 2026-11-21): it carries `phoxium.exe` only. `pixel-demo` stays in the repository (`cargo build --release -p pixel-demo`) as the target of the live checks; `package.ps1` and `release.ps1` no longer expect it.
- Developers: the crate is `crates/phoxium`, and every test and build variable `UCRT_*` is now `PHOXIUM_*` (`PHOXIUM_REQUIRE_GPU`, `PHOXIUM_COMMIT`, the `PHOXIUM_PROFILE_*` knobs of the profiles and benches), as are the GLSL macros.

### Fixed

- Frame pacing: moving pictures no longer step like 30 fps on the NVIDIA laptop. A few seconds after start, once the GPU lowered its clocks, the frames came in pairs (about 2 ms apart, then about 30 ms), in the framed window and in fullscreen alike, so only one frame of each pair could carry a new capture of a 60 fps game. The app now starts each frame after the next desktop composition (vsync and the FIFO swapchain unchanged). Measured on the RTX A2000 at 60 Hz (QUESTIONS OUT-6): frame intervals under 5 ms went from 32 to 49 % of all frames to none, the 95th percentile from 33 ms to 18 ms, and the frames that carry a new capture of pixel-demo from 50 % (one every 33 ms) to 90 % (one every 16.7 ms). The Intel UHD, which did not show the problem, is unchanged. Tests: `pacing` unit tests.

- Integer-scale detection: one frame no longer decides. When the captured window changed size (pixel-demo from 1:1 in a 900x720 window to integer x3 in 768x720, live 2026-11-21: 5 of 9 tries with v0.3.0, 0 of 8 with the fix), its first frame could still show the previous 1:1 picture, and that frame alone locked "native (x1)" for the session: the x3 game was treated as a 768x720 native raster. x1 is now taken early only after the first 6 informative frames all say so, otherwise the frames vote (a factor that at most 10 % of the other frames rule out is kept; native-looking frames give x1 only as the majority). Tests: `scaling` unit tests (stale frames after a resize, an odd frame among x3 frames, mostly native sources).

## [0.3.0] - 2026-11-20

ultimateCRT v0.3.0 is the second public release (MIT licence, binaries not code-signed). Since v0.2.0 the captured picture reaches the GPU without a trip through the CPU: zero-copy capture is the default, with an automatic fallback to the CPU copy and a Capture choice in the menu's Source section. The phosphor persistence trail was repaired (it could vanish when frames arrive unevenly) and has new afterglow controls; the Optics panel gains glow (bloom) and vignette controls and no longer lifts the blacks by itself, and the Geometry panel gains chromatic aberration controls. The output can be made click-through (`Ctrl+Alt+F6`), the window title and the menu show notices for a minimised source and for a move to a monitor driven by another GPU, and the framed window snaps to a screen edge. A three-model code review round and a live review fixed crash and robustness problems, notably an intermittent crash of zero-copy capture at attach, a persistence trail lost with uneven frame pacing, and a white flash when the window opens.

Known limits: the last fixes of this release (the zero-copy attach crash, the persistence trail, the window that now appears after its first frame) are covered by automated tests and by 45 consecutive zero-copy starts without a crash, but this exact build has not yet been re-checked by hand on an unlocked desktop (the picker without arguments, the white flash at start, the live persistence trail and the other interactive checks are still to be confirmed); zero-copy capture is not yet validated with a wide range of games and drivers (the Capture choice in the Source section goes back to the CPU copy); with click-through on, the framed window cannot be moved with the mouse; SDR output only; window capture only (no exclusive-fullscreen games); developed and tested on one NVIDIA laptop (AMD and Intel GPUs and other PCs are untested beyond it).

The entries below are the detail, grouped by Added, Changed, Fixed and Security.

### Added

- Zero-copy capture (`[global.capture] path`, `--capture-path auto|zero-copy|cpu` for one run; ARCHITECTURE A29). The captured client area is copied on the GPU into one of three textures shared between Direct3D 11 and Vulkan and read in place by the first stage of the chain, without the CPU read-back and upload: measured headless on the development laptop, the capture thread's copy drops from about 3.1 to 3.8 ms to 0.2 to 0.3 ms per frame at 2560 x 1440 (6.4 to 7.4 ms to 0.4 to 0.5 ms at 4K) and the upload goes (QUESTIONS CAP-2). The picture is bit-identical to the CPU copy. Zero-copy needs capture and rendering on one adapter and a driver that imports the textures. The automatic detections still read the picture back, about ten times a second. It is not yet validated with a wide range of games and drivers.
- A "Capture" choice in the menu's Source section, next to the attached program and Change source: "Zero-copy (GPU sharing, default)" or "CPU copy (most compatible)". It applies at once, in both directions, without a restart, and is saved (only when it is not the default). Below it, the path in force with its copy cost per frame and, when zero-copy is not running, why. On a PC that cannot share the textures the zero-copy entry is shown disabled with the reason. The Performance and diagnostics section shows the path in force, read-only.
- `--stats` prints the capture path in force and the capture thread's copy cost per frame; `--log` adds the `capture_path` and `capture_copy_ms` columns (after the GPU columns, so the earlier columns keep their position). The About section names the capture path.
- Glow (bloom) in the Optics panel: a soft, wide halo around bright areas that only moves light (a white screen keeps its level). Controls: weight (0 = off, up to 0.6), radius (0.5 to 60 mm on the tube face), falloff (a single Gaussian up to a long tail made of lobes at 3 and 9 times the radius), threshold (only highlights glow, soft knee) and a per-channel tint. Its weight shares the light with the halation and glare weights (their sum stays at 1 or less). It runs on the stage's image pyramid (each lobe on the level that matches its size); the `low` quality tier uses coarser levels. The README recipe: a gentle glow of weight 0.12, radius 6 mm, threshold 0.6 and falloff 0 keeps the blacks black; the wide lobes of a falloff above 0 lift them by a few codes.
- Vignette controls in the Optics panel: on or off on its own, corner brightness now down to 0 (black corners), start radius, falloff exponent, soft onset, round or following the picture's shape, floor, and an offset centre. At their defaults the vignette is the 0.2.0 one, bit for bit. The README gives validated recipes (black corners: corner 0, start 0.6, exponent 4, softness 0.2, roundness 0, edges at 99 % and corner black; strong vignette: corner 0.3, start 0.3, exponent 3, softness 0.3) and the tooltips of corner, start, exponent and roundness say so.
- The Optics panel is grouped (Glow (bloom), Vignette, Glass halo and glare, Phosphor diffusion, Tint and room), with the master switch as its first row and one sentence at its top saying that everything in it needs that switch (still off by default).
- Chromatic aberration controls (QUESTIONS PHY-17, ARCHITECTURE A30): a "Chromatic aberration" group in the Geometry panel of the settings menu, with a one-line explanation, for the coloured fringes of a real tube. `geometry_chroma_lateral_mm` (red and blue apart at the picture corner along the radius, red outward by half and blue inward by half, -10 to 10 mm, files up to 20), `geometry_chroma_axis_mm` with `geometry_chroma_angle_deg` (the same separation everywhere in one direction, 0 to 5 mm, files up to 20) and `geometry_chroma_edge_exponent` (growth from the centre, 1 to 3, default 2 like the radial convergence term). They add to the per-colour convergence controls, work in every beam path and quality tier (flat tile path, line-image path, reference form, curved warp path), and the skirt margin and the warp path's line-image pad grow with them, so a shifted colour is not cut at the picture's edge. Both amounts at 0 (the defaults) give the picture of the previous build bit for bit; presets unchanged. Oracle `crt_model::geometry::Chroma`; README "Colour fringes" advises 0.5 to 1 mm lateral for a monitor, 1.5 to 2 mm for a TV, axis 0.2 to 0.5 mm, and warns that above about 2 mm of lateral error a colour moire can appear at the sides. A per-colour spot size (per-gun focus) is a follow-up (PHY-17).
- Phosphor persistence controls for a clearly visible trail, beyond the measured P22 phosphor and off by default (the picture is unchanged until they are moved; QUESTIONS PHY-18): `phosphor_extra_afterglow_rgb` and `phosphor_extra_afterglow_time_ms`, an exponential glow per channel mixed into the phosphor's decay (red included, real time, a still picture keeps its brightness), and `phosphor_decay_scale`, a multiplier of every time constant of the measured decay. The menu's Phosphor panel opens with a short explanation of the trail and of its physical default; the README has a section with recommended values (for example an extra afterglow of 1.0 at 200 ms for a clearly visible trail).
- Click-through (ARCHITECTURE A32): `[global.output] click_through` (off by default), the hotkey `Ctrl+Alt+F6` (`toggle_click_through`, fallback `Ctrl+Alt+Shift+F6`) and a "Click-through (mouse to the game)" checkbox in the menu's Interface section. When on, the output ignores the mouse and clicks reach the window under it; the open menu or window list takes the mouse back, closing it returns to click-through, and F10 always opens the menu. "Reset everything to defaults" turns it off.
- Notices in the window title, the console and the menu's GPU and system section: "source minimised: no frames" for a minimised source or one on another virtual desktop (instead of a frozen picture and, 10 s later, "not drawing"; cleared when the window comes back); "moved to a monitor driven by another GPU: frames cross adapters (slower); restart to use that GPU" when the output is moved onto a monitor of another GPU (the GPU is never switched during a session); and a notice when the settings cannot be written (disk full, read-only folder, locked file), cleared by the next successful write.
- A simple snap for the framed output (whose own drag turns off Windows' snap): released at the left or right edge of a screen it takes that half, at the top edge the whole work area.
- Tests: the glow and vignette model against the f64 oracle (energy, radius, threshold, falloff, exact defaults, monotonic falloff, black corners, centre offset), the GPU against the oracle, a recorded fingerprint of the 0.2.0 vignette, the hard-bound sweep with the glow on, a typed value on the glow slider, the vignette recipes on the GPU (`vignette_recipes_keep_the_sides`), black levels in display codes through the whole chain (`look_recipes_whole_chain`), the chromatic aberration paths against the oracle and a recorded reference (`tests/stage_chroma.rs`, `tests/stage_chroma_reference.rs`: 17 scenes bit-identical to the previous build), the persistence trail through the whole chain (`tests/persistence_chain.rs`: defaults and all ten presets, 60 and 144 Hz frame periods, a moving bar in the display output), and a cost study of the glow run by hand (`glow_cost_study`). `Headless::set_frame_time_ms` gives headless frames a fixed frame period.

### Changed

- The default capture path is now zero-copy, with an automatic fallback to the CPU copy: the session uses zero-copy when the PC allows it (capture and rendering on one adapter whose driver imports the shared textures), else the CPU copy without a title notice (the console prints one line, the menu says why); any failure during the session falls back to the CPU copy by itself, with a notice in the console, the window title and the menu. A `settings.toml` without the key (every file written by v0.2.0) gets the new default; `path = "cpu"` stays the CPU copy. To go back to the CPU copy: choose "CPU copy (most compatible)" in the Source section, or set `[global.capture] path = "cpu"`, or run with `--capture-path cpu`. "Reset everything to defaults" puts the capture path back to the default. The Vulkan device now enables `VK_KHR_external_memory_win32` whenever the GPU can import the shared textures, whatever capture path is chosen, so that the path can be switched live; the CPU copy does not use it and its output is bit-identical with or without it (tested).
- The optics halation and glare weights (`optics_halation_weight`, `optics_glare_weight`) now default to 0 (were 0.015 and 0.01): switching Optics on lifted every black by 13 to 30 codes (measured through the whole chain: 13 codes far from a bright window, 28 beside it, 30 inside a black window in a white picture) even with the glow at 0, because the glass veil was on by default. Enabling Optics now gives exactly the effects you choose. The physical values stay in the tooltips (halation 1.5 %, glare 1 %: a glass veil lifts the blacks). The shipped presets keep their own explicit halation (1 to 3 %; presets 06 and 10 set none and now have none), still without enabling Optics; none sets a glare weight.
- `phosphor_tail_strength_rgb` goes up to 10 (log slider; above 1 is beyond the measured P22, and changes little at 60 Hz). Changing a tail strength or one of the new persistence controls restarts the persistence history primed to the picture, so a still picture does not flash while a slider moves.
- The automatic quality drop restarts its counting when the output moves onto another monitor, and the UI scale follows the new monitor's DPI also when the DPI message was missed (ARCHITECTURE A32).
- The capture restart onto the renderer's adapter falls back to the first adapter (CPU copy), then to the window list, instead of ending the session on a failure.
- Tooling: the temp-file cleanup of `release.ps1` and `package.ps1` is best-effort, so a cleanup failure (for example an 8.3 short TEMP path) can never change the exit code.

### Fixed

- Zero-copy capture (the default) crashed intermittently at attach, and once at a source resize (live review 2026-11-20: 10 crashes in 35 starts on the RTX, 4 in 5 on the Intel UHD, none in 12 with the CPU copy), with `range start index ... out of range for slice of length 0` in the integer-scale detection. Cause: while a detection runs every frame is read back for the CPU analyses, and when the main loop had not yet taken a frame's sample, the capture thread took that buffer to refill it for the next frame; the main loop could then take the earlier frame, marked as carrying its own pixels, with an empty buffer. The capture thread now leaves a sample that was not taken in place, and each frame records the size of the picture its buffer holds. The CPU analyses (black-frame check, Auto picture area, integer-scale detection, smoothed-source warning, the CPU upload and `--save-capture`) read pixels only through a checked sample (`capture::Sample`, new module `analysis`), and every detector refuses a buffer that does not hold its region instead of indexing it. Reproduced and covered headless in `tests/zero_copy.rs`; a fuzz test feeds the detectors random buffer lengths and sizes (QUESTIONS CAP-2).
- Phosphor persistence showed no trail at all in the window under uneven frame pacing, as after the A/B bypass in the live test of 2026-11-20 (the trail stayed 0 for 10 s until a restart). The window loop's measured frame periods alternate between about 1 ms and about 33 ms at 60 Hz when frames in flight let a frame be recorded right after the previous one; the automatic trail rate, a trimmed mean of 31 periods, then jumped by about 13 % with each new period and refitted the decay, which restarts the history primed to the picture, at nearly every frame (599 of 600 frames in the stage test): the picture was the one without persistence. The automatic rate is now the mean of the last 64 periods (a stall is capped at 2.5 times the mean), a new rate is taken only once it has settled, and each frame decays the trail by the mean period (a gap longer than three periods by its own length), so uneven intervals neither restart nor shorten the trail and it no longer flickers with the pacing. Tests: stage unit tests (alternating and phase-locked random intervals: at most one restart in 10 s, the step within 1.6 % of the period), `tests/persistence_chain.rs` (the whole chain with uneven pacing, the A/B bypass, and persistence off then on: the trail ratios equal the 60 Hz oracle within 1 %; 0 with the previous estimate), and `tests/stage_state_resume.rs` (the other stages that keep state across frames resume after the bypass and after their switch). A live moving-bar trail that looked shorter than the headless one is a measurement effect, not a defect (`live_bar_measurement_explained`); the red trail of 16 seen live is the SMPTE-C tube primaries of the preset seen in the panel's sRGB (0 with sRGB primaries). README "Phosphor persistence" gives both sets of numbers.
- A white area showed for about 0.3 s when the output window opened: the window is now shown once its first frame is presented (or after one second without one), and its client area is black until then.
- Zero-copy: after a capture restart, a reattach or a new attach, the renderer could keep sampling the previous session's shared textures (each session numbered its texture pools from 1); pool generations are now unique in the process and the renderer re-imports on any new pool.
- A DPI change queued in the same moment as the menu closing was dropped; a title-bar drag across monitors of different scaling now keeps the size Windows suggests.
- A wrong-typed `first_run_done` or `click_through` in `settings.toml` no longer makes the whole file unusable.

### Security

- Preset files are read at most 256 KB whatever size they report (import, and the presets folder at start): a larger file is skipped with a warning, the bound holds for a file that grows while it is read, and deep nesting and huge names give messages instead of failures.

## [0.2.0] - 2026-11-20

ultimateCRT v0.2.0 is the first public release (MIT licence, binaries not code-signed). It captures the window of a game or a program, runs it through a virtual CRT tube on the GPU and shows the result in a second window that can go fullscreen over the source without taking its keyboard focus; nothing is injected into the captured program. What is in it:

- A window picker (search, icons, preview), automatic detection of the integer upscale and of the picture inside black bars, per-game profiles, and reattachment when the captured window closes and comes back.
- The physical chain in linear light on the GPU (Vulkan, FP16): source decode, video amplifier, gun law and white balance, automatic beam limiting, scanline beam with spot growth, geometry and convergence, aperture grille, slot mask or delta dot mask, phosphor saturation and persistence, faceplate optics (halation, glare), SDR output transform; ten tube presets from published data; optional composite video, interlace, ageing and burn-in (all off by default).
- A settings menu inside the output window with every parameter live, preset management (save, rename, duplicate, import, export), rebindable hotkeys, an interface size setting, a quality tier (exact, standard, fast, low) with an optional automatic drop, and an About section.
- `pixel-demo.exe`, a demo and test source, and an offline `render` command.

The executables are not code-signed: Windows SmartScreen may warn on first run. Check the zip against the SHA-256 given in these notes (the README and `RUNNING.txt` say how). The bare F10 and F11 keys are global hotkeys while the program runs (both can be rebound).

Known limits: SDR output only; window capture only, so no exclusive-fullscreen games; developed and tested on one NVIDIA laptop (AMD and Intel GPUs and other PCs are untested beyond it) and checked live mostly with the bundled demo source and a few windows; several live checks are listed below as "not checked live". Frames go from the GPU to the CPU and back (a zero-copy path is a later step).

The entries below are the detail, grouped by Added, Changed, Fixed and Security. Ids such as T-48, R-05, D-01 or WP2 are task, review and work-package numbers of the project's own planning documents.

### Added

#### Window capture, picker and source
- `ultimatecrt`: window capture (Windows.Graphics.Capture, client area only, CPU copy) and Vulkan 1.3 output in a windowed or fullscreen non-activating window. The quit hotkey always quits.
- Source integer scaling: `--crop`, `--divisor` and automatic detection (x1 detected as native). Flat frames (a black boot screen) are not counted by the detector.
- Single-window product without a command line (owner requirement 2026-11-20, ARCHITECTURE A23 and 3.9, QUESTIONS CAP-7): started without options, `ultimatecrt.exe` opens its output window with a "Choose a window to capture" card (app name, hint, search, the capturable windows with icon, title, program, size and monitor, recent foreground windows first then alphabetical, minimised windows greyed with their note, a one-shot preview of the hovered or selected window with a refresh, keyboard Up, Down, Page Up, Page Down, Enter, Esc and double-click, "Show this list at every start"). The choice attaches through one path (source profile swapped, detection restarted, foreground handed to the chosen window, title naming the program). The settings menu has a Source section (detected native size, integer scale, capture area, Change source, Detach, ask at every start, wait for a closed window). New settings `[global.source] ask_at_start` (default true), `wait_s` (default 30) and `last` (executable, class, title; off: the last program is reattached at start when it runs). Pure logic in `picker.rs` (filtering, sort, search, selection, last choice, the source state machine NoSource -> Picking -> Attached -> Lost -> NoSource, preview plan and downscale) with unit tests; `sources::enumerate` and `sources::exe_icon` as Win32 glue; headless UI tests `tests/ui_picker.rs` with preview images in `target/ui-preview/picker-*.png`.
- Picture area, automatic by default, with manual limits (owner requirements 2026-11-20 after the failed live test, ARCHITECTURE A25 and 3.9, QUESTIONS CAP-7). The Source section's "Picture area" is **Auto** (default), **Manual** or **Whole client area**, stored per program and class (`[[source]] picture_area`, and `crop_client`: the client size manual limits were set for). Auto detects the picture inside the black bars at attach, whenever the captured client size changes and on **Detect now** (the old "Detect black bars"; it also resets the hysteresis), then keeps checking cheaply while frames arrive: frames sampled at most every 0.25 s and never more than 2 % of the time (the cost is printed by `--stats`), evaluated every 2 s; a larger or moved picture is followed after 3 evaluations in a row (a 1.5 s toast over a bar is ignored), a smaller one only after the bars stayed dark for 30 s, and black or flat screens change nothing (a fade or a dark scene never shrinks the crop). The area in force is shown ("detected · 256 × 224 at 329, 265 in 914 × 754"). Four limits **Left**, **Top**, **Right**, **Bottom** (px cropped from the client area) always show it; drag, Ctrl+click to type, or **-** / **+**; touching one switches to Manual from the values shown; **Snap to source pixels** (on, active with a known multiplier) moves them in whole source pixels; they never cross (8 x 8 px minimum) and stay in the window; applied live (placement, native size, scale detection, readouts), saved debounced. Manual limits are kept in pixels when the window is resized, with a warning that offers Detect now. **Back to Auto**, **Reset (whole client area)** and **Undo** (a drag or a run of nudges is one step). Pure logic in `bars.rs` (`Auto`, `AreaMode`, `edit_limit`, `clamp_limits`) with unit tests: the owner's geometry (256 x 224 at x1 and at x3 in 914 x 754), corner markers and a frame counter on a black picture, bright pixels on the picture edges, a dark scene with one bright frame, a 4:3 picture in 1280 x 720, the guard rails and their messages, attach and resize detection, a black start, a toast over a bar, growth and moves, fades and dark scenes that must not shrink, a real shrink after 30 s, the sampling rate, limit clamping and snapping, mode apply, reset and undo; settings migration test; headless UI tests in `tests/ui_source.rs` (mode combo, buttons, nudges, a drag with snapping, the resize warning) with previews `target/ui-preview/menu-source-area-*.png`. The optional "Show picture area" outline was not built: the menu shows no source picture to draw it on. The analysis is the one of the first "Detect black bars" button of the Source section, which this replaced: per-row and per-column maxima of the brightest channel over about one second of frames (so a dark scene is not taken for a bar when one frame lights it), bars within 8 codes of black, never a crop beyond a limit, the picture snapped inward to whole source pixels when the divisor is known, the result stored in the source profile of the program and class.
- Source scaling multiplier in the Source section (owner requirement 2026-11-20, QUESTIONS SRC-2): Auto (default, the detected value always shown, "detected: x3"), None (the capture is native) or x1 to x10, X and Y separately under Advanced ("Separate X and Y"). Applied live (native size, placement and readouts recomputed even without a new frame) and stored in the source profile (`divisor_mode`, `divisor`, `divisor_v`). A forced value wins over the detection; the detector now keeps running under a forced value so the hint "detected x3, forced x2" can be shown. A choice made in the menu replaces `--crop` or `--divisor` for the session. `scaling::Multiplier` maps the choice to `source_divisor_mode` and the divisor (unit tests: mapping, per axis, profile and settings-file round trip, source map). Headless UI tests `tests/ui_source.rs` drive the new controls by Win32 messages, with preview images in `target/ui-preview/menu-source-bars*.png`.

#### Physical chain (each stage has an oracle in `crt-model` and analytic GPU tests)
- Pipeline core: an FP16 `decode` stage (compute, native raster read at block centres) and an `encode` stage (explicit host EOTF, black surround around the tube rectangle), two frames in flight with per-frame uniform and staging buffers, images reallocated on source or native size change. Headless identity tests: all 256 codes per channel come back exact through the FP16 raster, FP16 subnormals kept.
- Source decode and tube placement (T-30): parameters `source_eotf` (`drive_voltage` default, or `srgb`: decoded to linear light, then drive voltage = L^(1/tube gamma)), `raster_aspect` (`par` default or `fill_tube`), `source_par`, `line_multiplier` (1 or 2), and the tube `tube_visible_height_mm` (290), `tube_aspect` (4:3) and `tube_height_fraction`. The CPU fills `px_per_mm` and `line_pitch_mm` of the frame constants (PVM-20M4U class on 2560x1440: 4.966 px/mm, 1.208 mm line pitch). With the defaults the picture is placed exactly as the old letterbox.
- Composite video (T-31, `signal` slot before the amplifier, `shaders/composite.comp`, `params/composite.toml`, oracle `crt_model::composite`, tests `tests/stage_composite.rs`; QUESTIONS PHY-9), optional, `composite_enable` off by default (the slot is skipped, bit for bit unchanged). NTSC or PAL composite or S-Video encode and decode of each native row at the source pixel clock (`amp_pixel_clock_mhz`), 8 samples per pixel: subcarrier phase per pixel, per line (180 degrees for NTSC timing) and per frame (`composite_frame_advance_deg`, 180 or 0: dot crawl), optional channel low-pass with burst-referenced colour gain, notch or 1-line comb separation (PAL: chroma delay line), I/Q (or U/V) chroma bandwidths, tint and colour. Gives chroma bleed, cross-colour (the artifact colours of 8-bit era games) and dot crawl. In the "Signal and amplifier" menu panel.
- Video amplifier (`amp` slot, `shaders/amp.comp`, `params/amp.toml`): Gaussian low-pass of the drive voltage before the gun law (`amp_bandwidth_mhz`, `amp_pixel_clock_mhz`), asymmetric rise/fall (`amp_fall_rise_ratio`), optional peaking (`amp_peaking_gain`, `amp_peaking_mhz`), K sub-samples per native pixel each holding the exact box mean of the amplifier output, clamped to the local input range (slew limiter); the defaults are an exact zero-order hold. Oracle `crt_model::beam::gaussian_step_box_mean`.
- Gun law and white balance (`gun` slot, `shaders/gun.comp`, `params/gun.toml`): `gun_law` power (default, 2.4), gog (contrast, brightness, per-gun cutoff and drive), bt1886 (Lw, Lb) and bt1886_annex1; optional white retune relative to the tube white, to the target `gun_retune_white_xy` (`gun_white_balance`, default off; gains (1, 1, 1) when the target is the tube white); the `srgb` source mode inverts the nominal curve of the active law and `gun_gamma` is clamped to >= 0.1; a disabled `gun` slot shows V as linear light, which is lighter than the gun-on picture. Oracle `crt_model::gun`.
- Automatic beam limiting and raster breathing (`abl` slot after `gun`, `shaders/abl.comp` and `shaders/reduce.comp`, `params/abl.toml`, T-35): the frame's mean beam current (GPU reduction, FP32) is low-passed on real frame times (`abl_tau_s`, default 0.1667 s) and lowers the beam current of the next frame above `abl_threshold_ma` (1.4 mA) with g = 1 / (1 + k max(0, I - I_th)), k set by `abl_full_white_ratio` (0.5); raster breathing `raster_scale` = 1 + `abl_breathing` (APL - `abl_breathing_ref`), used by the geometry stage (T-37); `abl_probe` diagnostic. Off by default (exact identity). Oracle `crt_model::abl`.
- Beam, vertical scanline profile (T-36a): each native row is drawn as a scanline whose Gaussian spot (plus an optional wide tail) is integrated over every host pixel, with the flat-field brightness independent of the spot width. Parameters `beam_fwhm_mid_mm` (default 0.45 mm), `beam_tail_weight`, `beam_tail_sigma_ratio`. Active once the tube is placed (px per mm and line pitch set); until then the screen stage keeps the nearest-sample copy.
- Beam, horizontal spot and spot growth (T-36b): along each scanline the amp samples are blurred by the same round spot and integrated over every host pixel (energy per source pixel conserved, flat fields unchanged), and the spot widens with each gun's beam current, FWHM^2 = d0^2 + k I^(2n). Parameters `beam_fwhm_peak_mm` (default 0.8 mm, PVM-20M4U) and `beam_growth_exponent` (default 0.5); `beam_fwhm_mid_mm` is the width at mid drive (beam current 0.5^2.4). Per-channel convergence hook in `beam.glsl`.
- Beam quality (T-36c): `beam_quality` `standard` (default, separable per workgroup tile, within 0.5 % of white mean of the exact form on the test patterns) or `reference` (exact 2D sum of every sample's own spot).
- Mask (T-39a, T-39b, T-39c): every host pixel takes the exact area average of the R, G and B phosphor elements it covers (pitch, fill and edge softness in physical units), normalised so that flat white keeps its brightness. `mask_type` selects the aperture grille (with optional damper-wire shadows), the slot mask (`mask_slot_period`, `mask_slot_bridge`) or the delta dot mask (`mask_dot_fill`). Below 3 host pixels per triad (and the matching limits vertically) the mask is averaged out by default (no host-grid moire), with a blend band `mask_tier_blend` and `mask_tier` to force either behaviour. Parameters `mask_enabled`, `mask_pitch_mm` (default 0.31 mm), `mask_stripe_fill`, `mask_edge_softness`, `mask_damper_count` (default 0), `mask_damper_width_mm`, `mask_damper_edge_mm`.
- Phosphor saturation (T-40, `phosphor_saturation`, off by default): L = I / (1 + s I) per channel before the persistence history.
- Phosphor persistence (`phosphor` slot, `shaders/phosphor.comp`, `params/phosphor.toml`, T-41): optional frame-to-frame afterglow from the measured P22 decay (Kuhn 2002): a bright frame leaves a green and blue trail of about 5.4 / 4.7 % of its light one frame later at 60 Hz, then about 3 % and 2 %, red none; a static picture keeps its brightness. Parameters `phosphor_persistence` (default off: the picture passes unchanged), `phosphor_frame_rate_hz` (60, the output refresh rate) and `phosphor_tail_strength_rgb` (0.07 to 1). The afterglow is cleared on a source size change and on a new capture session. Oracle `crt_model::phosphor::DecayFit::frame_feedback`.
- Geometry and convergence (T-37, `shaders/include/geometry.glsl`, `params/geometry.toml`): optional curved faceplate (`geometry_curvature` flat, spherical or cylindrical, `geometry_radius_mm`, `geometry_eye_distance_mm`; the raster lies on the surface uniform in arc length), residual pincushion/barrel, trapezoid and rotation, overscan per axis, and per-channel misconvergence (static dx, dy in mm plus a radial term growing toward the corners). ABL raster breathing (`abl_breathing`) now resizes the picture about the tube centre. The mask stays fixed on the tube. Every default is the identity: the picture is unchanged. The tube image carries a margin around the raster (`raster_margin`, 4 sigma of the spot at twice the peak current plus the largest misconvergence, limited by the room in the output) where the spot's skirt is drawn instead of cut; the live output adds it whenever the `screen` slot runs (a bypassed `screen` has no skirt and no margin). The `standard` beam quality keeps its separable fast path for the margin, overscan, `raster_scale` and misconvergence; a curved faceplate, pincushion, trapezoid or rotation use the two-pass fast path of T-91 (see Changed).
- Visible opening (T-37 review): the light of `screen` is clipped to the tube's visible area (`tube_visible_height_mm` x `tube_aspect`) with rounded corners, `geometry_opening_corner_radius_mm` (default 0, square; CRT.md 15 to 40 mm on older tubes): exactly 0 outside, antialiased over one host pixel along a curved outline. Not implemented and deferred (QUESTIONS PHY-11): S-linearity residuals (CRT.md has no residual profile) and refraction through the faceplate (no outer radius or glass thickness per curved tube).
- Faceplate optics (`optics` slot, `shaders/optics*.comp`, `params/optics.toml`, oracle `crt_model::optics`, T-44 and T-45; CRT.md rule 7, QUESTIONS PHY-10), off by default (`optics_enable`, D-6, D-24: the slot is skipped as an exact identity): phosphor-layer diffusion (`optics_diffusion_weight`, `optics_diffusion_mm`), the halation ring of the faceplate glass with its shape derived from the glass (`optics_glass_thickness_mm`, `optics_glass_index`, `optics_glass_transmission`: edge at 1.747 times the thickness, Fresnel haze inside, absorbed tail) and its amplitude as the fraction of light in the halo (`optics_halation_weight`, 1.5 %), veiling glare proportional to the mean picture level (`optics_glare_weight`), vignette (`optics_vignette_corner`, corner / centre), glass tint (`optics_tint_rgb`), diffuse room-light reflection (`optics_ambient_lux`, `optics_screen_reflectance`, `optics_white_nits`); all redistribute light, so a white field keeps its level. Halo method chosen by a headless cost study (`optics_halo_method`, `optics_halo_taps`): the exact kernel on one pyramid level (error 0.010 % mean, 0.13 % max of white; about 1.1 ms for the whole slot at 1920 x 1080 with every effect on, on a clock-limited GPU); a bloom-like pyramid mix and full-resolution Gaussians stay selectable for comparison. Optics panel in the settings menu (generated from the table). Presets 01 to 09 carry their faceplate thickness, halation weight and (05) transmission, and keep the stage off. Tests: `crt-model` oracle unit tests (ring position, kernel normalisation, Fresnel, FFT convolution, energy, vignette, glare, ambient), stage unit tests, `tests/stage_optics.rs` (identity bit exact, point-source ring and energy, edge, flat white and game-like frames against the oracle, diffusion energy, vignette ratio, glare linear in APL, tint and ambient, FP16 round to nearest) and the ignored cost study.
- Tube ageing (T-42, QUESTIONS PHY-14, `params/ageing.toml`, opt-in, `ageing_enable` off by default: the chain is unchanged bit for bit). Phosphor efficiency loss per colour from the hours of use (`ageing_hours`, `ageing_mean_level`, `ageing_white_cd_m2`), Pfahnl law 1 / (1 + c Q) with Q the charge in reference hours of full white at 350 cd/m2, calibrated on the one sourced point (15 % luminance loss after 20,000 h at 350 cd/m2) with relative colour rates (`ageing_rates_rgb`, default blue twice green, red half: white drifts warm); cathode wear per gun in `gun` (`ageing_cathode_loss_rgb`, `ageing_cutoff_drift_rgb`); spot growth of a worn gun (`ageing_spot_growth`, both beam widths scaled on the CPU so the skirt margin, the warp plan and the headroom readout follow). New chain slot `wear` between `screen` and `phosphor` (`shaders/wear.comp`), skipped as an identity while ageing and burn-in are off. Oracle `crt_model::ageing`.
- Burn-in (T-43, QUESTIONS PHY-14, SCP-6, `params/burnin.toml`, opt-in, `burnin_enable` off by default). This deliberately degrades the picture: static bright parts (a HUD, a letterbox edge, a logo) leave a ghost tinted by the colour that wore. A per-colour wear map of 640 x 480 texels over the tube's visible area (independent of the host resolution) accumulates the beam charge every frame (`shaders/wear_accumulate.comp`, exact area mean per texel, FP32 with compensated summation so real-time increments are not lost), at `burnin_acceleration` tube hours per real hour (1 = real time, 0 typed freezes the map), and lowers the efficiency with the same law as ageing. Saved per tube preset in `%APPDATA%\ultimateCRT\tubes\<preset>.state` (magic, schema version, size, CRC-32, atomic write; a missing, corrupt or other-version file is a new tube with a warning and a `.bak` copy; another size is resampled), every 5 minutes from an asynchronous GPU copy written on a background thread, when the preset changes, and at exit. A capture carries no field parity, so the user declares it: `alternate_frames_are_fields` (each captured frame is one field, the bottom field lands half a line pitch lower) or `split_woven_frame` (a woven frame: each refresh draws only the even or only the odd rows, at twice the line spacing, at their own positions). `interlace_field_order` (top or bottom field first) and `interlace_field_select` (alternate every output refresh, or lock the top or bottom field for inspection; a locked field of a woven frame is the 240p double-strike look). #### Quality tiers
- Quality tiers (T-48, QUESTIONS PRF-2; `params/quality.toml`, `src/quality.rs`, menu panel Performance): `quality_tier` = `exact` (the evaluation as before the tiers, bit for bit), `standard` (default: the beam of an unscaled flat tube on the line-image path, within one FP16 step of exact, `screen` 2.4 to 3 times cheaper on flat tubes), `fast` (also amplifier sub-samples capped to the host pixels per source pixel, at least 4, and the line-image path on scaled flat rasters; within 0.82 % of white mean, 2.7 % max), `low` (also a beam reach of 3 sigma, specialization constant 1 of `beam.glsl`, and a coarser warp grid; within 0.87 % mean, 2.7 % max). A tier changes cost parameters only, never a look parameter; a preset change keeps it. Measured cost and error per tier: ARCHITECTURE 3.7 "Quality tiers".
- Automatic quality drop on sustained overrun (QUESTIONS OUT-6; `quality::AutoQuality`, pure and unit tested): with `quality_auto` (off by default) the tier in force drops one step after 3 s of GPU frame time above the refresh period of the output's monitor (`output::refresh_hz`), and comes back one step after 10 s below 65 % of it (the wait doubles, up to 160 s, after a relapse within 30 s); the parameters are not changed (`Renderer::set_quality_drop`), the console, the window title and the overlay (row "Quality") show the tier in force.

- The window picker's search dropped characters outside the Basic Multilingual Plane (an emoji): Windows sends them as two UTF-16 surrogate units, which the picker handled one at a time; it now combines them (review D-14).
- The `encode` pass cost up to 3.5 ms at 1920 x 1080 (4.6 ms at 2560 x 1440) on detailed content (1-px checker, noise, game art with highlights) against 0.1 ms on flat content (T-47, T-93: "cause not found"): the clip counters were incremented with atomics on a host-visible storage buffer, so every clipping pixel sent an atomic across the bus. The counters are now in device-local memory, cleared on the GPU and copied to the host after the pass: `encode` costs 0.04 to 0.25 ms on every content. Measured by isolation: the shader without the atomics took 0.13 ms on the checker; a per-subgroup reduction of the counts in host memory did not help (the driver already merges a warp's atomics), the memory move alone did.

The 8-bit identity budget drops from 0.4968 to 0.311 of a code on an RGBA16F target (0.186 on an 8-bit target), the stage tests use the symmetric half-ulp window, and `gpu_fp16_store` checks the stores bit for bit against a CPU reference.
